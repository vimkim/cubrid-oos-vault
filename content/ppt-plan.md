OOS 는 무엇인가?

보통 RDBMS는 table 에서 하나의 row를 디스크에 연속적으로 저장한다. 이게 기본적으로 저장되는 단위는 DB에서 내부적으로 정한 DB page 크기만큼 저장한다. 보통 8K에서 16K 사이이다.

운영체제는 Disk를 읽어올 때 4K 씩 읽어오거나, 혹은 디스크 종류에 따라서 미리 prefetch 하는 등 여러 고려사항이 있는데 이는 대충 스킵하고,

RDBMS에서는 insert into … values () 일때 괄호 안에 들어가는 값들을 연속적으로 저장하는 것이 기본 가정이다. 많은 OLTP DB들이 그렇게 저장한다. 왜냐면 OLTP 디비들은 사용자가 디비를 사용할 때 column 단위로 전체로 가져오는 것보다는, range search 처럼 () 해당 레코드? 튜플? 에 해당하는 값들을 전부 가져오는 경우가 많다고 가정하기 때문이다.

그런데 OOS 는 디비에서 내부적으로 동작하는 최적화 방법으로, 만약 하나의 레코드에서 특정 컬럼의 크기가 너무 커진다면 이를 따로 저장하고, 기존 레코드 위치에는 OOS로 접근할 수 있는 디스크 포인터, 혹은 로케이터만을 저장해두는 방식으로 큐브리드를 수정하는 프로젝트이다.

Q. 왜 필요한가? 왜 이 프로젝트가 가치 있는가?

이 프로젝트의 가치는 매우 높다.

이 프로젝트를 우리 팀이 하지 않는다면 결국 어떠한 방식으로든 다른 팀이 다른 방식으로 어떤 형태로든 시도할 만한 가치가 있다. 다른 팀도 관심이 많다. 프로젝트가 빨리 도입되기를 원할 것이다. 다른 팀에서도 각각의 방식으로 훈수를 두고 있다.

왜냐하면 디비에서는 Disk IO가 성능에 가장 큰 영향을 주는 요인들 중 하나인데, OOS는 이 Disk IO를 특정 상황에 줄일 수 있는 근본적인 레벨의 최적화이기 때문이다.

온갖 최적화를 해보려고 해도, Disk IO 수가 크면 성능이 느려진다.

데이터베이스에서 Disk IO를 줄이는 것이 매우 중요하다.

그렇기 때문에 옵티마이저, 쿼리 프로세서들도 기본적으로는 Disk IO를 줄이는 방향으로 매우 고민을 많이 할 것이다.

그런데 DB는 여러 제약 사항들이 있다.

그것은 바로 ACID를 지키기 위해 마련해둔 많은 장치들인데, 쉽게 설명하면

하드웨어가 망가지지 않는 이상,

혹은 커널에서 버그가 일어나지 않는 이상,

사용자가 이 데이터는 꼭 저장되어야 한다고 선언하면 기필코 반드시 해당 데이터가 디스크로 내려가야 한다는 것은 자명한 사실이다.

그런데 매번 fsync 를 통해

데이터를 보존시키기 위해서 사용자가 데이터가 Disk 로 내려가는 것을 보장해야 한다.

Q. 현재 큐브리드는 어떠한가?

현재 CUBRID는 overflow page 구조를 사용하고 있다.

이는 기존 SQLITE 디비들에서 많이 사용되던 방법으로, 레코드 크기가 일정 수준 이상을 넘어서면, 원래 데이터가 저장될 heap page에서 빼서 다른 파일에 통으로 레코드를 저장하고 해당 page에 접근할 수 있는 정보만 넣어두는 구조로 만들어둔다.

현재 cubrid는 각 테이블 당 Overflow file 이 1개 생기며, 여기에서 Overflow Page를 관리한다.

즉, 하나의 Overflow file 이 관리하는 Page들은 모두 하나의 테이블에 소속된 것이며, 테이블마다 마구 섞일 일은 없다. 이에 대한 장점은? drop table 하면 그냥 page 들을 통으로 purge 하면 된다.

앞으로 큐브리드는 어떤 모습인가?

Overflow 구조를 배껴서 기본적으로 동일하다. 그냥 Overflow page 가 예전에는 독자적인 Overflow 페이지라는 타입이었다면, 이게 OOS page type으로 바뀌었을 뿐이다. 그리고 원래 Overflow page에는 최대 1개의 RECDES만 저장이 되고, 만약 RECDES가 너무 크다면 여러 개의 Overflow 페이지에 나뉘어서 저장이 되었다. 

OOS page는 이 구조가 slotted page로 바꾼 것 뿐이다. 이유는 내부 단편화를 좀 줄이기 위해서이다. 

Q. 왜 OOS page는 slotted page인가? 장단점은 무엇인가?

하나의 큰 recdes를 하나의 page레 저장하는 구조는 다루기가 엄청 쉽고, mysql 도 이 형식을 취하고 있지만, internal fragmentation이 발생한다는 단점이 있다.

안타까운 점은, mysql 은 이 internal fragmentation을 punch hole system call로 최적화하지만, CUBRID는 그런 최적화가 없다는 점이다.

이번에 바꾸는 김에 내부 단편화를 줄여서 disk io를 줄이기 위해 slotted page 구조를 채택했다.

단점은, 하나의 OOS page 에 두개의 서로 다른 Recdes에 소속된 OOS  값이 있다면, update 가 막히고 lock 이 걸려서 느려질 수 있다는 점이다. 두 개의 트랜잭션이 서로 다른 RECDES를 수정하는데도 lock 때문에 수정을 못하는 이슈 때문에 update 벤치마크가 overflow page (AS-IS)보다 느리게 나올 우려가 있긴 하다.

OOS 의 아키텍처는 어떤 구조인가?

CUBRID 개발자들을 위한 설명: Overflow File + Overflow Page와 기본적으로 동일하다.

각 테이블마다 하나의 OOS File 이 생긴다. 해당 File 에서 OOS page들를 관리한다.

그리고 Overflow Page type 대신 OOS Page type 을 사용한다.

Q. 이걸 왜 우리 팀이 해야 하는가?

기본적으로 큐브리드는 모든 것이 RECDES 를 가장 낮은 단위의 디스크 데이터 단위로 생각하고 있다. 그래서 Unloaddb, loaddb, network, heap 등등에서도 RECDES를 통으로 보낸다는 전제하에 고려된 api 가 엄청 많다. 로깅에도 RECDES가 통으로 저장된다.

이유를 생각해보면, RECDES는 정말 만능이다. 무엇이 문제인가?

근본적인 프로그래밍적으로 값을 다루는 법에 대해서 따져 보자.  

1. 프로그래밍 언어 레벨에서 사용 (혹은 Assembly level에서 CPU가 사용) 하기 효율적인 형식
2. 네트워크 상으로 전송하는 형식
3. 디스크에 저장하는 형식

이런 식으로 나뉘어야 하고, 모든 컴퓨터 프로그램은 시스템, 응용, 서버, 게임 분야 상관 없이 항상 위 3가지 형식에 대한 고려를 해야 한다. 그래서 어떤 도메인 혹은 프로그래밍 언어의 인기나 신뢰도를 판단할 때 항상 중요하게 고려해야 하는 것이 Serialization / Deserialization 인프라이다.

즉, 어떤 메모리 형태의 데이터를 전송하거나 디스크에 저장하는 형태로 효율적으로, 빠르고, 간편하고, 작게, 그리고 개발자 실수가 안 나오게 압축하는 것에 대한 고민을 항상 한다.

큐브리드는 그 Layer 를 독자적인 언어로 부르고 있는데,

1. DB 쿼리 프로세서에서 사용하기 편한 형식은 DB Value, Regular Variable 등으로 부르고 있고
2. 네트워크와 디스크에 저장하는 방식은 OR, Object Representation으로 부른다.

디스크에 저장하는 형태로 바꾸면 네트워크로 보낼 수도 있으므로 큐브리드에서는 이를 혼용하고 있다.

하나의 Record 를 구성하는 OR 값들이 모여서 RECDES의 payload 부분을 채우고, 이 앞을 Record의 header 값으로 채운다. 이 해더 값에는 각종 정보들이 적혀있다. 이 RECDES를 해석하려면 어떤 해석 정보를 사용해야 하는지 표시해둔 Representation ID, 그리고 각각의 Record 마다 다른 방식으로 해석하는 Variable Offset Table 등… 

여기서 문제가 발생한다. 사실, 아키텍처적으로 좀 편하게 사용하려면, Table 에 저장되는 하나의 Row, Tuple 을 의미하는 RECDES 는 전송용 Serialization 과 디스크 Serialization 과 구분이 되는 것이 깔끔하다.

그런데, 엄밀히 말하면 지금까지는 RECDES를 그대로 네트워크에 보내고, 디스크에 저장해도 문제가 발생하지 않았다. 그래서 코드 여기저기에 RECDES를 매우 여기저기에 마구 사용한다.

개발할 때 리팩토링을 하지 않는다면 가장 빠르고 직관적인 코드 형태지만, 이게 문제가 되는 이유는?

OOS를 도입하려면 이제 각각의 레이어에서 OOS locator 를 전부 고려해줘야 한다.

- 복구 로그
- 복제 로그
- 복구 일관성 (heap page와 OOS page의 sync가 맞지 않는 대참사)
- network serialization
- unloaddb (?)
- createdb (?)
- CDC (?)

이런 걸 다 하려면? 사실 스토리지 레이어를 다루고 있는 우리 팀만이 할 수 있는 업무이다 .

Q. 근데 우리 팀만이 할 수 있는 건 사실, 최대한 storage api를 사용하도록 아키텍처를 짜서 그런 거 아닐까?

왜 하필 현재 구조로 잡았나?

다른 좀 더 간단한 아키텍처로 간다면 3, 4팀에서도 할 수 있지 않을까?

Q. 예를 들어, overflow 파일을 그냥 간단하게 큰 친구들만 보내도록 바꾸면 어떨까?

1번째, 4팀에서 제안한 방법인데, 너무 크게 바꾸지 말고 대충 Overflow page 형식을 배껴서, Overflow 에 다 보내는 형식 말고 간단하게 큰 컬럼만 Overflow page로 보내는 형식으로 hacky 한 방법으로 대충 바꿔버리면… 많이 변경하지 않고도 가능할 수도 있다. 견적을 내보지는 않았다. 누가 한번 시도해보면 좋겠다. 그래도 여전히 네트워크 레이어나 unloaddb, createdb, 로깅에서는 커다란 RECDES 를 일단 보내버리고 overflow 파일에서는 각각의 서버에서 알아서 처리하므로, 아무 소용이 없다. 해당 부분을 여전히 고쳐줘야 한다. 그래서 좀 손이 많이 든다.

Q. 그러면 pg처럼 내부 toast 테이블을 사용하는 방법은 어떤가?

혹은 pg처럼 내부 테이블을 생성해서 인터널 table api를 사용해서 대충 내부 테이블로 해결하면 문제가 쉽게 해결될 수도 있다. 이에 대한 리서치는 진행하지 않았다. 한번 시도해보고 성능 측정해서 누가 공유해주면 좋겠다. 대충 락을 여러번 걸어야 할 거 같아서 성능 저하가 발생할 거 같아서 지레 겁먹고 안했는데, 누가 락 모듈에 대한 깊은 이해도가 있다면 진행해볼 만 하다. 만약 하나의 테이블에 넣기 너무 큰 데이터가 있다면 쪼개서 넣으면 된다. 무엇보다 pg의 레퍼런스가 있어서 진행해볼 만 하다. 락도 그렇고, 두 테이블의 transaction sync 도 맞춰야 한다. 동일한 transaction을 가져간다고 가정하거나, 아니면 두 개의 transaction이 무조건 같이 commit 된다고 고려해야 한다. 

또 페이지에 논리적 키를 저장하는 방법이 있고, physiological 한 OID를 저장하는 방법이 있는데, 전자는 성능 문제가 걱정되고, 열심히 구현해두었는데 현재 overflow file 구현보다 느려지는 참사가 발생할 수도 있다. 그래서 접근하기 무섭다. 예를 들어, 테이블의 레코드를 수정할 때, 해당 레코드에 OOS 가 있으면, 해당 레코드 OOS가 있는 내부 테이블에 select 해서 또 접근해서 해당 페이지에 해당 OOS 가 저장된 부분들에 모두 (쪼개져 있는 부분에) 여러 page fix를 할 때까지 기다려야 하는데, 성능 저하 우려가 있다.

그렇다고 또 다른 테이블에 저장되는 OID를 적어두면 그건 현재 구현이랑 slotted page 랑 차이가 없는 것이다. 그리고 OID 저장 방식은 어차피 replication 에서 두 서버의 OID가 같다는 것이 보장이 안되므로 처리를 해줘야 한다는 문제가 발생한다. 

그리고 해당 api 들도 팀에서 익숙하지 않다. heap, slotted page는 나름 팀원 전원이 내공이 많이 쌓이고, api 자체가 너무 low 하다 보니까 시간 투자만 조금 하면 금방 무슨 역할을 하는지 ai가 알 수 있지만, 상위 api 로 top 으로 올라갈 수록 너무 추상화되어 있어서 내공이 많이 필요하다.

기본적으로 pg는 2001년부터 pg를 도입하여 toast 에 최적화되어 진행되어 왔기 때문에 그 내공이 우리 아키텍처에 안 맞을 수 있다는 위험성이 있어서, 조심해야 한다.
